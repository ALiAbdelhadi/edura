# Load test — ERP + superadmin, per role (2026-09-20)

**Scope:** `apps/erp` (six portals) and `apps/superadmin` (two), production builds,
served by `bun --bun next start` on Bun 1.4.2, against a **local** Postgres 18.4.
**Nothing in this campaign left localhost** — see §1.
**Harness:** [tests/load/](../../tests/load/README.md) (k6 v2.2.0). Raw artefacts:
`tests/load/results/` (gitignored).

> **How to read every number here.** Each one names how it was produced. Anything
> that is arithmetic on top of a measurement says so, and §7 is the only place
> prices appear — those are list prices recalled, not measured, and are marked.

---

## 0. The five things that matter

1. **The counter's cash path could deadlock the whole instance — found, proven,
   fixed.** `createWalkInSubscriptionTx` opened a second transaction
   (`assertNotBlacklisted`) while holding the first. With a pool of 10, ten
   concurrent cash payments each hold one connection and wait for an eleventh.
   Measured: 90 concurrent requests → **0 accepted, 450 × P2028, every request
   31–60 s**, and because the pool is shared, *every other request on the instance
   stalls with it*. After a 2-line hoist: the same burst → **162 accepted, 113 ms
   mean, 0 errors**. On the counter ramp, 250 VUs went from 8.5 req/s with 46%
   timeouts to 288–412 req/s with none (§4.1).
2. **No double charge, anywhere, under any load we produced.** 17,815 real cash
   payments through the real engine; after every run payments = ledger rows =
   accepted requests, 9/9 invariants (§5). Firing the same payment three times at
   once: exactly one `201`, the rest `422`. The DB's partial unique index
   `subs_one_active_pass` is what holds — the service check alone would not.
3. **One instance is one JavaScript thread, and a dashboard page costs it 6.4 ms.**
   That is the ceiling: ~155 full page renders/s, or ~2,100 cheap API calls/s.
   Postgres was never the limit for six of eight roles. 17% of page CPU is
   `JSON.stringify`/`parse` of a **192 KB translation dictionary shipped on every
   dashboard page** — all eight portals' strings plus the marketing site's, to a
   student. **Fixed in this change**: each portal now receives only what its code
   can reach. True A/B on the student home: **−24% HTML, −20% gzipped bytes,
   +7.6% page renders/s** (§4.2). An earlier, rougher experiment suggested +33%;
   that number was wrong for the safe version and is withdrawn there.
4. **Raising the DB pool does nothing** (10 → 30: 430 → 448 req/s, inside noise).
   It looked like the bottleneck — 10/10 connections "idle in transaction" — but
   that is the *symptom* of a saturated JS thread, not the cause (§4.3).
5. **1,000,000 req/s is not a target this product can have.** It is four times
   *every student and one parent in Egypt using Edura in the same second*, and
   ~125× the peak of a platform serving 1,000 centres. The realistic peak —
   100 centres, every student checking in inside 30 minutes — is **178 req/s on the
   counter path: one fixed instance at the edge of its knee, two with 2× headroom**
   (§6, §7).

| Rate limiting, auth, RLS | Untouched in code. Many clients are simulated the way production sees them: one `X-Forwarded-For` per virtual user. `ALLOW_UNSHARED_RATE_LIMIT=1` (the documented single-instance hatch) is set **in the test process env only**. |

**Fixture shortcuts, stated plainly:** (a) seeded `subscriptions` are coverage
without a payment (`payment_id NULL`, `is_demo`) so a covered check-in can be
exercised; (b) back-office load accounts get `two_factor_enabled=true` by SQL after
sign-in, so the TOTP step itself was not load-tested; (c) one bcrypt hash is shared
by all 30k load accounts.

## 2. Method

- **Data:** 20 centres × (1 owner, 3 receptionists, 10 teachers, 2 assistants,
  1,000 students, 500 parents); 400 groups of 100; 8,400 lessons (one *today* per
  group); 640,000 attendance rows; 40,000 enrolments; 30,390 users.
- **A virtual user** is one signed-in person with a pre-minted session cookie and
  its own client IP, viewing one screen at a time with a 1–3 s pause. A page view =
  the route's HTML (a full server render — see below) + the API calls that screen
  fires on mount, batched in parallel like a browser. Writes are the one or two the
  role really performs.
- **Ramp:** 10 → 50 → 100 → 250 → 500 VUs, 2 min per step; the first 15 s of each
  step (VUs still climbing) is excluded from that step's numbers.
- **Knee, computed not eyeballed:** the last step with unexpected-status ≤ 1% **and**
  p95 ≤ max(3 × first-step p95, 500 ms). Steps are coarse, so the true knee lies
  between the reported step and the next one.
- **Evidence per run:** status-code distribution per step; app / Postgres / k6 CPU
  and `pg_stat_activity` states every 5 s; `pg_stat_statements` top 15; money-table
  census + invariants before/after. A run with a sampling gap > 20 s (a sleeping
  laptop) is marked INVALID automatically — one was, and was discarded.

### Three facts that decide whether any number here means anything

1. **Limiter vs server.** `withRateLimit` keys on `(path, client IP)`. Every
   scenario here measures **the server**: each VU has its own IP, so no role's mix
   drew a single `429` (status tables, §3). The limiter itself was not the subject;
   the routes it guards (`checkout`, `wallet-topup`, `search/courses`, sign-in) are
   listed in §8 as not load-tested beyond that.
2. **Every page is dynamic.** The nonce CSP makes the route census
   360 dynamic / 3 static / 0 prerendered. Not one HTML response is a cache hit:
   each is a full React server render (measured 6.4 ms of CPU for a dashboard).
   **Comparing these numbers with a "typical Next.js app" that serves static or ISR
   pages from a CDN is meaningless** — that app does no work per page view; this
   one does all of it.
3. **Eight roles, eight query shapes** — tested separately, reported separately.

### Two caveats that bound every number

- **One machine.** k6, the app and Postgres share an Apple M5 (10 cores, 16 GB).
  The app is single-threaded, so it never competed for a core with k6 (k6 ≤ 18% of
  one core, recorded per step) — but see the next point.
- **Machine noise moved results by ~2×.** The first full campaign ran overnight with
  ~2 cores of background load (Spotlight `dasd` 86%, WindowServer, a browser;
  load average 6). Re-run on a quiet machine, the same build and scenario roughly
  doubled: parent at 100 VUs went from 112 req/s / p95 2,171 ms to 196 req/s /
  p95 31 ms. **§3 reports the quiet run**; the noisy run is kept in §3.3 because it
  is what a shared or burstable vCPU looks like, and because it is the run in which
  the counter deadlock first appeared.

## 4. Bottlenecks, with evidence

### 4.1 Pool deadlock on the counter's cash path — FIXED in this change

**Where:** `packages/server-core/src/services/subscriptions/subscriptions.ts` —
`createWalkInSubscriptionTx` (runs inside the caller's `scopedDb` transaction)
called `assertNotBlacklisted`, which opens its **own** `platformDb` transaction
(`services/blacklist/blacklist.ts:250`). It has to be a separate, platform-context
transaction — under RLS a tenant-scoped one cannot see platform-level blacklist
rows (`blacklist_entries` policy: `rls_bypass() OR center_id = current_center_id()`)
— but it does not have to be *nested*.

**Why it deadlocks:** each request holds connection #1 and waits for #2. With
`DATABASE_POOL_MAX=10`, ten concurrent cash payments hold all ten and wait on each
other until Prisma's `maxWait` (10 s) fires; `transactionWithRetry` then retries the
inner one twice more while the outer still holds its connection, up to the 20 s
transaction timeout. It is *metastable*: below ten in flight it never shows
(a quiet-machine ramp sailed through 250 VUs at p95 78 ms); once latency rises for
any reason, in-flight count crosses ten and the instance does not recover while
load continues.

**Evidence:**

| measurement | before | after the fix |
|---|---|---|
| Burst: 30 VUs × 3 identical concurrent cash payments (90 in flight), pool 10 | **0 accepted** of 450; all 450 failed after 31–60 s; `P2028` × 450, "Unable to start a transaction in the given time" × 350, "expired transaction" × 200; `pg_stat_activity` at t = 8 s: **10 / 10 `idle in transaction`, last statement `set_config('app.current_center_id')`, tx age 8 s** | **162 accepted**, 738 refused `422` (already covered), 0 errors; mean 113 ms, p95 234 ms; payments Δ = 162 |
| Counter ramp, 250 VUs (overnight run) | 8.5 req/s, **46% timeouts**, app CPU 15% (idle!), 10/10 idle-in-tx | 412 req/s, 0 errors, p95 50 ms |
| Counter ramp, 500 VUs | 15 req/s, **63% timeouts** | 536 req/s, 0 errors, p95 625 ms |
| Counter knee (last healthy step) | 50 VUs / 89 req/s | 250 VUs / 412 req/s (run `fix1`); 100 VUs / 159 req/s (run `quiet`, where 250 VUs gave 288 req/s at p95 875 ms) — both with 0 errors |

The stall is not confined to the money route: the pool is shared, so at 250 VUs
*every* endpoint on the instance — the roster, the lookup, the staff home page —
showed p95 = 30 s.

**The fix (in this change):** the blacklist check moved to the two callers, before
they open the transaction — `createWalkInSubscription` and
`adminCreateWalkInSubscription` (`apps/superadmin/.../center-money.ts`). Same check,
same order, same refusal; the race it leaves (a blacklist landing in the
millisecond between check and insert) existed before too, since the check never
locked anything.

**The same pattern, second site — also fixed:** `enrollStudentTx`
(`services/center/enrollments.ts`) made **two** nested `platformDb` calls (course
lookup + `assertNotBlacklisted`). Extracted to `assertEnrollmentNotBlacklisted`,
called by both callers before their transaction.

**Third site — NOT fixed, reported:** `createCollaborationRequestTx`
(`services/collaboration/collaboration.ts:177`) calls `resolveCenterAdmins` inside
its transaction. Low concurrency in practice (collaboration requests are rare), but
it is the same bug. A static scan of all 173 `tx`-taking functions found these
three; the other 14 hits were inside post-commit `effects`, which is the correct
pattern.

> **Production note.** On Vercel each function instance has its own pool of 10 and
> serves concurrent requests, so the precondition is "10 concurrent cash payments
> *on one instance*" — rarer than on a single server, but one busy evening at a few
> large centres is enough, and the symptom (everything times out, CPU idle) would
> have been very hard to diagnose from production logs.

### 4.3 The connection pool is a symptom, not a cause

At saturation every role shows 9–10 of 10 connections `idle in transaction`,
waiting on `ClientRead` — Postgres waiting for *the app* to send the next statement.
That reads like pool starvation. It is not:

| parent, 250 VUs | pool = 10 | pool = 30 |
|---|---:|---:|
| req/s | 430 | 448 |
| p95 | 524 ms | 418 ms |
| app CPU | 125% | 132% |
| connections idle-in-tx (max) | 9 | 21 |

Teacher: 393 vs 397 req/s. More connections just means more transactions parked
while the single JS thread gets to them. **Do not raise `DATABASE_POOL_MAX` to fix
latency**; on Neon it multiplies connections per instance for nothing.

What *is* real: **every DB access is an interactive transaction**
(`BEGIN` → `set_config` → queries → `COMMIT`, `packages/database/src/client.ts:184-198`),
and one request often opens several in sequence — the teacher dashboard opens four
(`reports.ts:1021` + three at `:1058`). Locally a statement round trip is ~0.1 ms;
on Neon it is a network hop. A request measured here at 6–10 statements will hold
its connection 10–30 ms longer in production *per transaction*. See §8.

### 4.5 Sign-in is ~18 /s per instance

Minting 500 sessions at concurrency 4 took 27 s ⇒ **18.5 sign-ins/s** on one
instance (`bcryptjs` is pure JS on the same single thread, ~55 ms each). With 30-day
sessions this is invisible day to day. It is the number that matters the morning
after a mass sign-out (secret rotation, a `token_version` sweep): 10,000 users
signing back in is ~9 minutes of one fully-blocked instance. Native bcrypt
(`Bun.password`) is ~10× cheaper and off-thread — but password hashing is
security-critical code; treat it as its own reviewed change.

## 5. Money — did load ever break the books?

**No.** After every run, and at the end of the campaign:

```
rows: payments=17815 transactions=17815 walk_in_passes=17815
  ok    no (student, session) holds two active passes
  ok    every active walk-in pass has exactly one payment
  ok    no payment is shared by two subscriptions
  ok    no orphan payment (a charge with no coverage behind it)
  ok    payments and ledger payment rows are equal in number
  ok    payments and ledger payment rows are equal in value
  ok    every paid walk-in pass has exactly one ledger payment row
  ok    one attendance row per (session, student)
  ok    receipt numbers are unique
```

| check | result |
|---|---|
| Accepted requests vs rows, race test A (9 concurrent, 120 triples) | 71 × `201` ⇒ payments Δ = **71**; 0 triples with two `201`s |
| Race test after the fix (90 concurrent, 300 triples) | 162 × `201` ⇒ payments Δ = **162**; 0 double charges |
| Counter ramp during the deadlock (overnight) | `201` seen by client = 2,803; timeouts/500s = 289; payments Δ = **2,832** — i.e. **29 payments committed whose response the receptionist never saw** |

That last line is the one real money-adjacent finding. `POST /center/subscriptions`
takes **no idempotency key**. When the response is lost, the receptionist sees an
error while the cash *is* recorded. Nothing double-charges — a retry is refused by
`subs_one_active_pass` with `422 "An active pass for this session already exists"`,
and the client re-checks coverage before retrying — but the operator's screen said
"failed" for a payment that succeeded. With the deadlock fixed the window is
ordinary network loss, not a systemic stall. A `clientRequestId` (the pattern
`payouts` and `payments` refunds already use) would let the retry return the
original receipt instead of a refusal.

Aside, not a load finding: a subscription payment's ledger row carries
`payment_id = NULL`; the only link from `transactions` to its `payments` row is the
subscription id inside the free-text `notes`. The reconciliation here had to match
on `notes LIKE '%subscription <id>)'`.

## 7. What 1,000,000 req/s would take — and whether it makes sense

**Arithmetic (measured unit costs × the target):**

```
app:       1,000,000 req/s / ~150 req/s per vCPU at the knee (ERP roles: 95-419)  = ~6,700 vCPU
           + 40% headroom                                                          = ~9,500 vCPU
postgres:  ~0.25 core per 100 req/s (measured range 0.12-0.50)                     = ~2,500 cores
writes:    3-8% of requests are writes                                             = 30,000-80,000 write transactions/s
egress:    ~30 KB per response after gzip (measured 25-282 KB raw; pages 427 KB -> 95 KB)
           1,000,000 x 30 KB = 30 GB/s = 240 Gbit/s                                = ~78 PB / month
```

What that implies structurally — none of which exists today:

- **Read replicas are not enough, and the app cannot use them yet.** Every read
  runs inside an interactive transaction on the primary (`withTenant` /
  `withPlatformContext`); there is no replica routing. 2,500 cores of Postgres with
  30–80k write tx/s is beyond one primary with any number of replicas — it means
  **sharding by centre** (the tenancy model would allow it: RLS already keys on
  `center_id`), on the order of 10–20 shards, each a 32–64 vCPU primary with 3–5
  replicas, plus a cross-shard story for students, parents and the ledger.
- A shared rate-limit store doing 1M ops/s, a CDN in front of everything static,
  and a queue for every notification that is sent inline today (D4).

**Monthly cost, order of magnitude only.** Unit prices below are list prices as I
recall them, **not measured and not verified today** — check before quoting:

| item | quantity | unit price (recalled) | per month |
|---|---:|---|---:|
| app compute | ~9,500 vCPU | $25–40 / vCPU-month on cloud VMs (serverless "active CPU" pricing is ~2–3× that) | $0.25–0.9 M |
| Postgres | ~2,500 vCPU + storage/replicas | ~$100–120 / vCPU-month managed | $0.25–0.3 M |
| egress | ~78 PB | $0.02–0.05 / GB at volume | **$1.6–3.9 M** |
| Redis, logs, monitoring, support | | | $0.1–0.3 M |
| **total** | | | **≈ $2–5 M / month**, dominated by bandwidth |

**Does the target make sense? No.** Egypt has roughly 25 million pre-university
students (A, public figure). If *every one of them and one parent each* used Edura,
and 5% were active in the same second making a request every 10 s:
`50,000,000 × 0.05 / 10 = 250,000 req/s`. One million req/s is **four times the
entire country using the product simultaneously.**

What is realistic, from §6's measured ratio (~765 req/s per 100 busy centres):

| scale | peak req/s | app | Postgres | rough cost (same recalled prices) |
|---|---:|---|---|---|
| 100 centres / 100k students | ~0.8 k | 8 vCPU | 4 vCPU | a few hundred $/month |
| 1,000 centres / 1M students — the dominant national platform | ~8 k | 55–80 vCPU | 16–32 vCPU + 1–2 read replicas | $3–6 k/month |
| 1,000,000 req/s | 1,000 k | ~9,500 vCPU | sharded, ~2,500 cores | $2–5 M/month |

Engineer for the middle row. It is 125× below the million, it is reachable with the
current architecture plus the fixes below, and the first thing that breaks on the
way there is not throughput — it is the unbounded queries in D1–D4 as data grows.

### The three cheapest fixes, ranked by MEASURED effect

| # | fix | cost | measured effect |

| 1 | **Hoist the nested blacklist transaction out of the cash path** (§4.1) — *done in this change* | 2 call sites, ~10 lines | 90-concurrent burst: **0/450 accepted → 162/162 clean**, mean 53 s → 113 ms. ## 8. What was NOT tested

- **Neon.** The pg driver on localhost, not `@prisma/adapter-neon` over WebSocket
  to eu-central-1. Every request here is 6–10 statements across 1–4 interactive
  transactions with ~0.1 ms round trips; production pays a network hop for each.
  Expect higher latency and longer connection hold times than anything above.
  The repo's own record of this effect: the DB suites ran **~90× slower** on Neon
  than locally. **This is the largest unknown in the whole report.**
- **Vercel's runtime.** Production is Node on Vercel functions (autoscaled, cold
  starts, per-instance pools), not `bun next start` on one box. Per-vCPU cost
  should be the same order; concurrency behaviour is not the same.
- **The shared Redis rate limiter.** Runs used the in-memory fallback. In
  production every rate-limited request adds a Redis round trip (1.5 s deadline,
  breaker after 3 failures).
- **gzip.** k6 requested identity encoding; `next start` would spend extra CPU
  compressing 427 KB pages (Vercel's edge does this in production, not the function).
- **Rate-limited routes under load:** sign-in, `subscriptions/checkout`,
  `payments/*/initiate`, `search/courses`, walk-in registration. Online checkout,
  the Paymob webhook, wallet top-up/pay-from-wallet, **lesson settlement
  (`distributeSessionRevenue`)**, payouts and refunds were not exercised — the only
  money path under load was cash-at-the-counter.
- Push/email/WhatsApp fan-out (mock / console drivers), Cloudinary uploads, CSV
  import, report export, cron jobs. (The chat WebSocket server is covered in §8a.)
- **Door check-in** (`counter_and_door` mode) — all seeded teachers are `counter_only`.
- **The TOTP step** of back-office sign-in (fixture shortcut, §1).
- **Soak / leak behaviour.** Longest run 10 minutes. App RSS rose ~600 → 820 MB
  within runs; not investigated.
- **Bigger data.** 20 centres / 640k attendance rows. D1–D4 will be worse at 10×.
- **Browser-side cost**, and **in-app navigation realism**: every page view here is
  a full HTML render; a real session after first load navigates by RSC payload
  (measured 5× cheaper). Real throughput per instance lies between the two.
- **Multi-instance behaviour** — nothing here ran more than one app process.

### A second pool deadlock — in the shared database package — FIXED

`roleGuardExtension` (`packages/database/src/extensions/index.ts`) runs a one-time
`SELECT current_user…` on the **root** client, but every operation awaits it —
including operations already inside an interactive transaction. On a cold process,
if `pool max` transactions begin together, each holds a connection while waiting for
a check that needs one more. Nothing moves until the 20 s transaction timeout.

| 400 sockets arriving at 200/s on a fresh server | before | after |
|---|---|---|
| time until a socket's post-connect DB work finished (p50 / p99) | **19,127 ms / 20,056 ms** | **1.7 ms / 71 ms** |
| transactions killed (`P2028 … expired transaction … 20000 ms`) | 10 | 0 |
| reproduced | 6 runs of 6 | 0 runs of 6 |

In production terms: **every redeploy of the chat server with users online froze chat
for 20 seconds and failed the first ten connections.** The ERP only escaped it because
its first query per request happens to be a non-transactional session read; the chat
server's first query per socket is inside a transaction. The fix (`primeRoleGuard`,
called from `createPrisma`) starts the check when the client is built — before any
transaction can hold a connection. The guarantee is unchanged: every operation still
awaits the same promise, so nothing is served before the role is known and an unsafe
role still refuses every query. Both apps' DB suites pass after it (91 + 38 suites).

**Knee: ~1,600 messages/s** (p99 already stretching to 148 ms); the ceiling is
~1,640/s. Past it nothing is lost or duplicated — it queues: rows written 230,916 =
199,812 acked + 31,104 that committed after the client had stopped waiting;
`(conversation_id, client_id)` duplicates: 0.

What that means in people (A: someone actively chatting sends one message per 20 s):
1,600 msg/s ≈ **32,000 people typing at the same moment**. A hundred busy centres is
more like a few hundred, i.e. < 20 msg/s. **Throughput is not the sizing dimension for
this server; memory per open socket is: 20 KB idle, ~35 KB with 9,000 users' presence
state** (≈ 190 MB base + 35 MB per 1,000 sockets).

Each message costs Postgres two transactions (~8 statements): ~1 core per 800–1,000
msg/s. On Neon each statement is a network round trip, so **the Railway region must be
the one nearest Neon's eu-central-1** (EU West); from a US region every message would
pay ~8 transatlantic round trips. Not verified here — check the Railway dashboard.

**Structural limit, stated plainly: this server cannot be run as two instances today.**
Presence (`PresenceRegistry`) and rooms are in process memory; a second instance would
not see the first one's users, so messages between them would silently fall back to
"offline → push". Scaling out needs the Socket.IO Redis adapter plus shared presence —
not built. One instance carries 10,000+ sockets, which covers the first two growth
stages; it is the thing to build before the third.

**Not tested here:** typing and read-receipt events, the offline → push path
(`notifyOffline` calls the ERP), group chats, TLS (Railway's edge terminates it), the
token endpoint under a reconnect storm (10,000 reconnects = 10,000 `GET
/realtime/token` on the ERP; measured ERP cost for a simple authenticated API call is
0.47 ms, so ~5 s of one instance), and everything over a real network.
