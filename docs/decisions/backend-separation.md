# Backend separation — apps/api + apps/admin-api

**Status: ACCEPTED 2026-09-29 (Ali's decisions below). Phase 1 built; every later
phase waits for Ali's go.**

## Goal

apps/erp and apps/superadmin become frontend-only: UI, routing, SSR shells. No
database access, no business logic, no auth server, no cron, no webhooks in either.
All of that runs in two standalone Bun services that deploy on their own.

Non-goals: any behaviour change, any schema change, any new product capability.
Moving code is a MOVE; a behaviour fix found on the way is a separate change.

### Where the brief's picture was incomplete

1. **Authorization is not one wrapper.** superadmin uses `withRole` (240 of 253
   handlers). The ERP uses five guard shapes: `requireRole` 105, `centerStaff` 61,
   `requireSession` 56, `delegated` 19, `delegatedWithCenter` 17 (+ combinations,
   `cron-secret`, `internal-secret`). `centerStaff` and `delegated` WRITE audit rows
   after a successful mutation (`center-actor.ts:129`, `teacher-actor.ts:72`). Each
   shape ports as-is, side effects included — no unification during the move.
2. **22 ERP handlers carry no guard pattern.** Hand-checked: they are the intended
   public doors (auth register/forgot/reset/invite/view-as claim, contact,
   csp-report, public search/profile/subjects, health, `_ping`) and the Paymob
   webhook, which verifies HMAC inside `resolveDriver().verifyWebhook`
   (`payments/paymob/webhook/route.ts:15`).
3. **~31 client components import pure helpers from the server packages** —
   `@repo/server-core/lib/date-key`, `@repo/database/student-code`,
   `@repo/database/grading-scale`, `services/sessions/conflict-detector`,
   `services/students/student-card`, `services/payments/receipt-document`. They are
   isomorphic and run in the browser today. A blanket
   `no-restricted-imports` on `@repo/server-core` / `@repo/database` breaks the build.
   They must first move (unchanged) to a browser-safe package; the lint rule then
   bans only server entry points.
4. **`packages/server-core` depends on `next`** (peer + 3 files import
   `next/server`); routes return `NextResponse`. A Hono service must not load Next.
5. **Session reads are implicit.** `requireSession()` reads `next/headers`, not a
   `req` argument. Rewriting 450 call sites to pass `req` is a rewrite, not a move.
6. **Public data is cached in Next's data cache** (`"use cache"` + `revalidateTag`:
   catalog, discovery, public profiles), invalidated cross-app through
   `/api/v1/internal/revalidate`. That cache does not exist outside Next.
7. **Deferred work uses `after()`** (`lib/http/after.ts`, with a microtask fallback).

## Decision

### Two services, Bun + Hono

- `apps/api` serves everything under apps/erp's `/api/**` today; `apps/admin-api`
  serves superadmin's. Separate processes, separate deploys, separate secrets where
  they are separate today. A shared process would put the back office behind the
  ERP's door, which CLAUDE.md forbids.
- **Hono** (one new dependency, `hono`, in the two services only). Why: its
  handlers take a Web `Request` and return a `Response`, which is exactly the shape
  every route here already has, so a route ports through a thin adapter with its
  body untouched. Rejected: bare `Bun.serve` (we would hand-write routing and param
  matching for 450 paths — new code where a move is wanted); Elysia (Bun-only idioms,
  schema-first handlers — a rewrite).
- Both import `packages/server-core`; no service code is copied into either app.
- `apps/realtime` stays as it is (already a Bun service on Railway).

### Making the move a move

Three enabling changes, each behaviour-neutral and each proven by the existing
suites before any route moves:

1. **Request context.** server-core gains one `AsyncLocalStorage` request context
   (headers, cookies, client IP). The Next adapter fills it from `next/headers`;
   the Hono middleware fills it from `c.req`. `requireSession()` and friends keep
   their signatures.
2. **`next` out of server-core.** `ok()` / `fail()` / `withErrors()` return a plain
   `Response` with identical status, body and headers (`NextResponse` extends
   `Response`, so Next routes keep compiling). `after()` becomes an injected
   scheduler: Next's `after` in the frontends, fire-and-forget in the long-running
   service.
3. **Isomorphic helpers** (item 3 above) move to a browser-safe package with
   re-exports left behind until phase 4 removes the old paths.

### Routing: same origin, strangler by prefix

- Browsers keep calling same-origin `/api/v1/*` and `/api/auth/*`. Each frontend's
  `next.config` gains `rewrites().beforeFiles` entries to the service, one prefix
  per area as it passes parity. `beforeFiles` wins over the still-present Next route,
  so rollback is deleting one rewrite line. The Next route is deleted only after
  parity passes. Cookies stay first-party, CSP is unchanged, no CORS.
- **CDN caching of proxied responses.** Vercel honours upstream `Cache-Control` on
  external rewrites (default for projects created on/after 2026-04-06, per Vercel's
  rewrites docs, read 2026-09-29). The services therefore reproduce today's headers
  exactly — `withPublicCache` routes keep their `s-maxage`; every other response
  carries the `no-store` that `ok()` sets today (`public-cache.ts:2`) — and the parity harness diffs
  `Cache-Control` as well as status and body. Money, wallets, subscriptions,
  attendance, messaging, auth/session and per-user data are never cacheable.
- **Client IP.** The service must not trust a header the browser can set, and
  whether Vercel's external rewrite overwrites `x-forwarded-for` is not proven. So
  `src/proxy.ts` (whose matcher already covers `/api`) stamps the platform-derived
  IP (`trustedClientIp`, unchanged) into `x-edura-client-ip` plus
  `x-edura-proxy-auth` = a new shared secret (`EDURA_PROXY_SECRET`). The service
  uses `x-edura-client-ip` only when the secret matches and otherwise falls back to
  its own platform header (Railway's edge header: to be proven in phase 2 with the
  same method as `m3-rate-limit.test.ts`). Traffic that hits the service directly
  (cron, Paymob, realtime) takes the fallback path.

### Auth

better-auth is instantiated only in the services: the ERP instance in `apps/api`,
the back-office instance in `apps/admin-api` (two doors, two cookie sets, as now).
`baseURL` stays the frontend origin (`NEXTAUTH_URL`) so cookies are still minted for
the host the browser sees. Unchanged: `token_version` / L1, `sendResetPassword` NOT
set, suspension only via `users.status`, `login-policy.ts`, the 60-second view-as
handoff and the one-hour window from `auth_sessions.created_at`. Server components
that gate on the session (portal-gate layouts, onboarding, receipts, print pages,
`c/[payload]`, `p/[handle]`, sitemap) call the service server-to-server, forwarding
the cookie and the stamped IP — one extra hop per SSR request.

### Public data cache

The Next data cache is replaced by a tag-keyed cache in server-core over the Redis
that production already requires (`REDIS_URL`), holding ONLY what is cached today
(catalog, discovery, public profiles), with the same TTLs, and invalidated by the
same tags through `/api/v1/internal/revalidate` (now on `apps/api`). An in-process
map is not enough once a service runs more than one replica.

## Risks

| risk | mitigation |
|---|---|
| A move silently changes behaviour (status, messageAr, headers, audit rows) | parity harness diffs status + body + `Cache-Control` + `Set-Cookie` names + resulting audit rows; 100% before any rewrite flips |
| A private response cached at Vercel's CDN | explicit no-store on every non-public response; parity on the header; a test that fails if a money/auth path is cacheable |
| Client IP spoofable → rate limits decorative | proxy-stamped IP with shared secret; proven like M3 before auth moves |
| One JS thread per service instance (load test 2026-09-20; one nested-tx pool deadlock site left) | ≥2 replicas; fix that deadlock site before money moves; rate limit already in Redis |
| Extra network hop on every API call and SSR page | same EU region; measure p50/p95 in phase 2; abort criterion agreed before phase 3 |
| Two deploy targets drift (frontend expects a route the service lacks) | services deploy first; rewrites per prefix; the inventory JSON as the checklist |
| A backend deploy no longer purges the CDN (public routes) | TTL ceiling unchanged (≤ 1 h); purge by tag from `internal/revalidate` if needed |
| Service boots without a required secret | reuse the fail-closed boot checks (`assertSharedRateLimitStore`, secret asserts) in both services |
| 19 ERP tests import route modules | they move with the routes and run against the service |

## Phases (unchanged order, with the enabling work placed)

1. Consolidate `apps/*/src/lib/services/**` into server-core (zero behaviour change),
   plus the three enabling changes above. Thin routes.
2. `apps/api` skeleton (request id, errors → envelope, rate limit, session, the five
   guard shapes, health, observability) + parity harness + IP and latency proofs.
3. Strangler: reads → writes → auth → money → webhooks/cron.
4. Frontend purge + `no-restricted-imports`.
5. Phases 2–4 for `apps/admin-api`.
6. Cutover document (Ali executes).

## Phase 1 — what was built (2026-09-29)

- **`packages/shared`** (`@repo/shared`): `date-key`, `student-code`,
  `grading-scale`, and the pure half of the conflict detector as
  `schedule-clash`. Moved unchanged; the old paths
  (`server-core/lib/date-key`, `database/queries/{student-code,grading-scale}`,
  `services/sessions/conflict-detector`) re-export them until phase 4. Client
  components import `@repo/shared/*` directly. Nothing in it may import a
  database, a secret or a Node-only module.
- **server-core carries no `next` import.** `ok()` / `fail()` / `withErrors()`
  build a plain `Response` (same status, body and headers — `NextResponse.json`
  was `Response.json` plus a wrapper nothing here used). `next` left its
  dependencies.
- **Two injected seams** replace the Next APIs server-core used:
  `http/after.ts` (`setAfterScheduler` / `runAfter`, microtask fallback kept) and
  `http/request-context.ts` (`runWithRequestHeaders` over `AsyncLocalStorage`,
  with a registered fallback source). Each Next app registers Next's `after` and
  `headers` in `src/lib/http/next-bindings.ts`, loaded by its envelope shim; the
  Hono service will bind them per request instead.
- **Services consolidated.** `apps/erp/src/lib/services/**` →
  `server-core/src/services/**`; `apps/superadmin/src/lib/services/**` →
  `server-core/src/backoffice/**`, a separate namespace so the phase-4 lint rule
  can keep the ERP service away from back-office code. The ERP wallet facades
  were renamed `wallet-facade` / `parent-wallet-facade` to avoid colliding with
  core's own wallet module. Imports inside core are relative; app files that
  imported a moved module were repointed, and one-line shims to moved modules
  were deleted.
- **What stays in the ERP app until phase 3:** the Next data-cache adapters
  (`services/catalog/catalog-read.ts`, `discovery/discovery-cache.ts`,
  `public-handles/public-profiles-cache.ts`, `public-profile-for-request.ts`) and
  the React `cache()` wrapper `public-handles/public-profiles.ts`. Their DB reads
  moved to core as uncached `read*` functions; the adapters wrap them with the
  same `"use cache: remote"` / `cacheTag` / `cacheLife` / `cache()` as before.
- **Routes thinned**: the route files that still held `scopedDb` / `platformDb`
  work now call a named core function; guards, rate limits, cookies and cache
  headers stay in the route.

## Phase 2 — what was built (2026-09-30)

- **The ERP auth layer is host-neutral.** `server-core/src/erp-auth/create-auth.ts`
  holds the better-auth options once (`createErpAuth({ extraPlugins })`); apps/erp
  passes `nextCookies()` (still last), the service passes nothing. The session
  readers, view-as and the five guards (`authz/require-role`, `center-actor`,
  `teacher-actor`) moved unchanged; app files re-export them. Proof: the
  `auth.options` of the old and new ERP instance compare equal key by key,
  including function sources, plugin order and the 43 endpoints.
- **Two more seams:** `setRequestMemo` (React `cache` in Next, the ALS store in the
  service) and `setUserTagger` (who the request is for, for Sentry).
- **`apps/api`** (Bun + Hono 4.13.11, `@sentry/node` 10.71.0): request id, client
  IP, request context, access log, session user slot, the core error envelope,
  `/api/health` (the ERP handlers, moved to `server-core/http/health-route.ts`).
  `nextRoute()` mounts an unchanged Next route export. `session-seam.ts` registers
  the service's auth instance and tagger. Sentry's `setUser` is not per request under
  `Bun.serve`, so the identity is kept per request and set on the captured
  event's own scope. No route has moved yet.
- **Boot refuses** without the shared rate-limit store, and in production without
  `EDURA_PROXY_SECRET`, an `https://` `NEXTAUTH_URL` and `NEXTAUTH_SECRET` (the
  Next app's AUTH-09 check keys on `VERCEL_ENV`, which Railway never sets).
- **Client IP:** implemented as described under Routing. `proxy.ts` strips both
  edura headers on every `/api/**` request on the canonical host and stamps only
  when the secret is set; `server-core/http/proxy-client-ip-trust.ts` verifies in
  constant time and writes the vouched IP into the slot `trustedClientIp` reads
  first. An `/api` URL with a dot skips the proxy matcher and takes the fallback
  path (no such route exists).
- **Deliberate difference:** an unknown `/api/v1/*` path answers with the
  `NotFoundError` envelope; Next answers with its HTML 404 page.
- **Not proven (needs a staging deploy, Ali's call):** that Vercel forwards
  middleware-set request headers across the external rewrite; which header
  Railway's edge sets; the real Vercel→Railway p50/p95.
- **Parity harness and local latency:** `apps/api/tests/parity/` (`test:parity`,
  local `edura_test` only) runs the SAME ERP route module through the Next shape
  and through `createApp()` + `nextRoute()`, with real better-auth sign-ins, and
  diffs status, body, `cache-control`, set-cookie names and audit rows: 24/24
  cases match (health; `/me` for six roles + 401; catalog; one route per guard
  shape; 403/404/400; two audited non-money writes). In-process overhead of the
  Hono stack: about +0.03 ms p50 (health 0.180 → 0.209 ms; `/me` 1.786 → 1.745 ms).
- **Session cookies on the service.** Found by the harness: a server-side
  `auth.api` call (the session refresh after `updateAge`) extended the row but the
  service sent no cookie, because that is `nextCookies()`' job in Next.
  `apps/api/src/session-cookies.ts` is its port, in the same last plugin slot:
  the RSC no-refresh rule, the raw set-cookie strings collected per request, and
  Next's merge rule (`appendMutableCookies`: the route's own cookie wins, else the
  last value per name). For the RSC rule to hold once SSR calls the service,
  those server-to-server calls must forward `RSC` and `next-action`.
- **Open for phase 3, found by the harness:** routes behind the `"use cache"`
  adapters (`catalog/subjects?all=1`, `?gradeLevelIds=`) throw outside a Next
  runtime, and `revalidateTag` from the service reaches no cache (caught and
  logged). Both are the Redis public-data cache above; those routes move with it.
- **Open for phase 3:** `auth/view-as/claim` and `auth/view-as/stop` import the
  Next app's `auth` instance directly, not `erpAuth()`. They must switch to the
  registered instance when they move, or the service would hold a second
  better-auth instance (own limiter and hooks).

## Phase 3 — what was built (2026-09-30)

- **Every ERP route moved.** The 243 handlers live in
  `apps/api/src/routes/<path under /api>/route.ts`; each ERP `route.ts` is now a
  shim that binds the Next host (`@/lib/http/route-host`) and re-exports the
  handler, keeping its own `dynamic` exports. `apps/api/src/routes/index.ts` is
  generated (`scripts/gen-routes.ts`, `--check` in the unit suite) and mounted with
  Next's method rules (HEAD runs GET, OPTIONS lists the sorted methods, anything
  else is a bare 405). ERP source-scanning tests read a route through
  `tests/route-source.ts`: the shim, then the handler it re-exports.
- **Route order is part of the contract.** Hono answers with the first registered
  match; Next prefers a fixed segment over a dynamic one, and a dynamic one over a
  catch-all. Plain alphabetical order put `[` before letters, so 13 fixed routes
  were shadowed on the service (`payments/[id]` answered `payments/initiate` with
  405). Found by the parity sweep. The generator now orders segment by segment the
  way Next does, and `routes-mount.test.ts` fails if a dynamic route precedes a
  fixed route it would match.
- **Auth runs on the service.** `auth/[...all]` is `erpAuth().handler` (plus the
  unchanged sign-out revocation); view-as claim/stop use the registered instance.
  Their 303s are built from `erpPublicOrigin()` (= `NEXTAUTH_URL`, better-auth's
  own `baseURL`), not from the request URL, which names the service behind the
  rewrite. `viewAsRedirect` builds the Response the way `NextResponse.redirect`
  did (null body, same `Location`). Dev cookies carry the port
  (`edura-<PORT>`); the service reads `EDURA_DEV_COOKIE_PORT` first so it matches
  the ERP it sits behind. Production is `edura` on both.
- **Public data cache** (`server-core/src/cache/public-store.ts`) as decided above,
  keyed `pubcache:v1:<env>:<tag>:<gen>:<sha256(name, args)>`; a tag bump is an
  INCR, and old entries expire on their TTL. Both hosts bind
  `bumpPublicDataTag` as the invalidator. No `"use cache"` directive remains;
  `experimental.useCache` in `apps/erp/next.config.ts` is now unused (left for
  phase 4).
- **Money, webhook, cron, exports** moved as-is: the Paymob webhook, the cron
  runner, `reports/export` (still `buildReportExport`, the screen's function) and
  the data-rights export. The CSP reporter got a seam (`setCspReporter`) bound to
  `@sentry/nextjs` in the ERP and `@sentry/node` in the service.
- **Found and fixed on the way:** `createCollaborationRequestTx` read the centre's
  admins through `resolveCenterAdmins`, which opened a second pool connection
  inside the caller's transaction (a nested-tx deadlock at pool size). It now
  reads them on the caller's transaction.
- **Local hop proof (dev):** ERP rewrite → a capturing hop → `apps/api`. A
  browser-set `x-edura-client-ip` is stripped and the real IP stamped with the
  proxy secret, the query string arrives unchanged, and a signed-in student's
  `/me/unread-counts` answers 200 with `no-store` on the service.
- **Parity:** 2718/2718 on local `edura_test` — the registry sweep (every route ×
  every method anonymously, GET × seven roles) plus 74 targeted cases: better-auth
  sign-in/out and session, view-as claim/stop with their audit rows, cron auth,
  the Paymob webhook's refusals, CSP reports, both exports, and the public cache
  across hosts (a write through either host is seen by both; a direct SQL change
  with no tag bump is not). A money-table guard proves the run wrote no money row.
  Not provable locally: better-auth's Origin check (off under `NODE_ENV=test` on
  both hosts), a real Redis between two processes, webhook paths that settle money.
- **Rewrites:** `SERVICE_PREFIXES` lists every area (`/api/auth` and each
  `/api/v1/<area>`), one line each so an area rolls back alone; `/api/health` stays
  on the ERP because it reports on the ERP. `tests/unit/service-routes.test.ts`
  fails if a listed area still holds a route that is not a shim, or if a route is
  left uncovered. Inert until `API_SERVICE_URL` is set, which is cutover (phase 6).
  Local browser check (dev DB, student): the dashboard loads with every `/api`
  call answered by the service through the rewrite.

## Phase 4 — what was built (2026-10-01)

- **The ERP is frontend-only.** `apps/erp/src/app/api/**` (243 files) and 34
  server-only files under `src/lib` are deleted. `apps/erp/src` holds no value
  import of `@repo/server-core`, `@repo/database`, `@repo/notifications`, Prisma,
  `ioredis`, `bcryptjs`, `jose`, `nodemailer`, `@sentry/node`, the `api` workspace
  or better-auth's server entry. `apps/erp/eslint.config.mjs` enforces it
  (`@typescript-eslint/no-restricted-imports`, `allowTypeImports: true`, so the
  `ErpAuth` type still types the browser client). The patterns are regexes: a
  plain `api` group also matched `@/lib/api/client`, and a `!better-auth/react`
  re-include did not apply.
- **Rewrites are unconditional.** `serviceUrl()` is `API_SERVICE_URL`, else
  `http://localhost:${API_PORT ?? 3006}` outside production. A production server
  without it throws; a production BUILD does not (CI builds env-less), except on
  Vercel production, where `next.config.ts` refuses the build. The config's
  default export is a function so the build phase reaches `serviceUrl()` — Next
  sets `NEXT_PHASE` only after the config is loaded. `/api/health` now goes to
  the service too (same body, status, HEAD and `?deep=mail`): the ERP has no
  database to report on. Consequence: the ERP deploy health gate in `deploy.yml`
  (not edited) also fails when the service is down.
- **Server components read the service through one helper.**
  `apps/erp/src/lib/server/service-fetch.ts` forwards the cookie, `rsc`,
  `next-action`, `accept-language` and `x-request-id`, stamps the client IP the
  way `proxy.ts` does (only the stamped header and the proxy secret cross, never
  a browser-set one), and is `no-store`. `ssr-session.ts`, `staff-me.ts` and
  `lib/auth/portal-gate.ts` sit on it. A service failure throws to the page's
  error boundary; no page carries a fallback of its own.
- **Seven new service routes, all `no-store`**, each a thin door on the
  server-core function the page used to call in-process, with that code's tier
  and tenancy: `v1/me/ssr-session` (`getSessionUser`, `isOnboardingComplete`,
  `getViewAsContext` — never a second copy of their null rules; signed out is
  200 with `user: null`), `v1/payments/[id]/receipt-document`,
  `v1/reports/print` (the export's tier and the screen's function),
  `v1/students/scan/[payload]`, `v1/public/profiles/[handle]`,
  `v1/public/pricing`, `v1/public/sitemap-handles`. The public profile's
  anonymous read stays on the shared public cache; the cookie/editor read is
  never cached. Pricing keeps its database-error fallback inside `readRates`;
  the fee functions did not move.
- **Browser-safe helpers moved unchanged to `@repo/shared`**: handle rules,
  public host, second language, deep link, room amenities, phone, app URL,
  client IP, proxy client IP, public pricing, and the portal-segment table.
  `login-policy.ts` changed only by that move: it re-exports the table and
  keeps the `Role` checks as compile-time assertions; `LOGIN_APP` and
  `canSignIn` are byte-identical.
- **Tests followed the code.** 41 ERP unit files that test routes or server
  libraries moved to `apps/api/tests/unit`; ERP DB suites import
  `@repo/server-core` and `api/routes/*` directly and bind auth through
  `tests/db/helpers/bind-auth.ts`. The parity harness lost its ERP twin, so side
  A is now the handler called the way Next called it and side B the same module
  mounted in the Hono app: 2816 cases over 250 routes. The new routes have no
  twin; each is tested against the direct server-core call plus its 401/403/404.
  One harness race was fixed: the view-as claim's `auth.login_succeeded` row is

## Phase 6 — the cutover document (2026-10-01)

Document only; nothing was deployed and production was not touched. The steps
Ali runs, the variable tables for both services and both frontends, the proofs
that need the real Vercel → Railway hop, the rollback, and the list of things
still proven nowhere are in
[backend-cutover](../runbooks/backend-cutover.md).

Three things that runbook makes explicit and the earlier phases did not:
`deploy.yml` must be held until the services are live (the phase 4/5 build is
refused or points at nothing otherwise); no latency abort number was ever
agreed, so it has to be set before cutover from pre-cutover measurements; and
each backend carries its own Railway config (`apps/api/railway.json`,
`apps/admin-api/railway.json`) — root `railway.json` is the realtime service's.

Closed the same day, before the commit: CI runs the superadmin, api and
admin-api unit suites, the generated-route-table check and both parity suites,
and boots `apps/api` beside `apps/erp` for both E2E jobs (the frontend has no
backend of its own any more). The parity guards accept CI's loopback `neondb`
only when `CI=true`. Both parity suites were run locally with exactly the
variables CI writes, on local `edura_test` (test): they fail without
`SUPERADMIN_BASE_URL` / `ERP_BASE_URL` / `NEXTAUTH_URL` (7 redirect and
revalidate assertions) and pass with them, so the workflow sets them on those
steps. The workflow itself has not run on GitHub. The env tooling
(`scripts/setup-env.ts`, `scripts/gen-vercel-env.py`, `turbo.json`,
`.env.production.example`) listed three Paymob variables nothing reads and
omitted the one the code requires outside mock; it now lists
`PAYMOB_INTEGRATION_IDS`.

The CI jobs were then rehearsed on a clean copy of the working tree — no env
files, `bun install --frozen-lockfile`, a throwaway database on local Postgres
labelled `edura-env:test`, migrated and seeded by the workflow's own commands,
dropped afterwards. That found one real break: `ky` had left
`apps/superadmin/package.json` with the backend while a unit test still imports
it, and a stale local symlink hid it; a frozen install failed the superadmin
type check. It is back as a dev dependency. With that: the build passes with no
environment at all (so the placeholder secrets are gone from the build step),
type check and all four unit suites pass, the E2E smoke passes 7/7 against
`apps/api` + `apps/erp` booted exactly as the workflow boots them, and the five
Playwright matrix entries pass (role-guard 8, student 10, teacher 9, admin 13,
parent 10). Three tests needed their one retry; one of those was the per-IP
sign-in limit answering 429 after five runs back to back from one address,
which a fresh CI runner per matrix entry does not reproduce.
`scripts/gen-vercel-env.py` now writes six sheets — `.env-api` and
`.env-admin-api` for Railway — and the two frontend sheets carry no database or
auth secret. Both Railway files use only keys and values in Railway's published
schema and mirror the realtime service's live config; no service was created.
