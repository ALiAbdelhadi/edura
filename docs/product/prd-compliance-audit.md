## 1. Executive summary

### Stack reality vs PRD
The PRD recommends **Express/NestJS + PostgreSQL + React Native + React web**. The repo is a **Next.js 14 App Router monolith** (API route handlers under `app/api/v1/**`, React web dashboards under `app/[locale]/**`) on **Prisma + Neon Postgres with row-level security**. This is a deliberate, previously-approved hybrid reconciliation: the existing per-center "Edura" product (Course→Session→Enrollment, where **Session ≈ PRD "lesson"** and **Room ≈ PRD "classroom"**) is kept, and the PRD's marketplace layer (super_admin/accountant, platform fee, transactions/invoices/payouts, points, blacklist, audit) is added on top. `apps/www/AGENTS.md` is **stale** (describes a since-replaced Mongoose stack); the code is 100% Prisma. Endpoint paths therefore deviate from the PRD in naming while being capability-equivalent — each row cites the actual path.

> **Notes:** CONCURRENCY IS THE WEAK SPOT. All money paths run inside a single Prisma interactive transaction (packages/database/src/client.ts:96-104) at Postgres default READ COMMITTED — no isolationLevel, no row locking, no advisory locks. Correctness against double-spend currently rests almost entirely on the ACCIDENTAL protection of the refNumber unique index colliding, because ref numbers are generated from tx.transaction.count() (distribution.ts:79, payouts.ts:129). That same mechanism makes ANY two concurrent ledger-writing operations (two teachers completing sessions, a payout approval during a completion) abort one of them with a P2002 — a guaranteed failure under load and a hard scale bottleneck (count() is O(n) over an ever-growing append-only table, executed on every distribution and payout). Fix pattern: a Postgres sequence (or per-year sequence) for ref numbers + a partial unique index on transactions(lesson_id) WHERE type='commission' (per fromEntityId) as a real idempotency constraint, and status-guarded UPDATE ... WHERE status='pending' RETURNING for payout settlement (settlePayout at payouts.ts:107-111 has a read-then-write race; double-approve is again only saved by the refNumber collision). Other cross-cutting observations: (1) ledger immutability is app-layer only (Prisma extension) — no DB trigger/REVOKE UPDATE,DELETE on transactions, so $executeRaw or direct SQL can still mutate; the runtime role edura_app is NOBYPASSRLS but not write-restricted on transactions; (2)
